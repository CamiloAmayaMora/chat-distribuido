1La idea en 1 minuto

Analogía: un sistema de correos. El profesor tiene la oficina central de correos. Cada grupo del curso tiene una sucursal (nuestro servidor). Los usuarios (ana, beto…) le entregan sus cartas a su sucursal; la sucursal las manda a la central, y la central le entrega una copia a todas las demás sucursales. Las sucursales nunca se mandan cartas entre ellas. Todas las cartas van a un único tablero público: la sala #general.

Lo difícil no es mandar una carta: es qué pasa cuando algo se cae.

  • ¿Y si la central está cerrada cuando quiero enviar? → guardo la carta y la reintento después.
  • ¿Y si envío dos veces la misma carta por si acaso? → cada carta tiene un número único (id) y quien la recibe bota las repetidas.
  • ¿Y si mi sucursal estuvo cerrada y me perdí cartas? → al abrir le pido a la central "mándame lo que me perdí".
  • ¿En qué orden pongo las cartas en el tablero, si cada reloj de pared marca una hora distinta? → con un contador de Lamport.

Eso es todo el proyecto. El resto es cómo lo programamos.

2Cómo ejecutarlo paso a paso

Lo único que hay que instalar

  1. Docker Desktop (docker.com). Ábranlo y esperen a que diga "Engine running".
  2. Python 3 (solo para el cliente de consola, las pruebas y el experimento).
Docker es como una "caja" que trae todo lo que el programa necesita (Python, librerías…). Por eso funciona igual en cualquier computador: no hay que instalar FastAPI ni nada más.

Opción A — Probar todo en un solo portátil (lo que usamos para la demo)

Abrir una terminal (PowerShell) en la carpeta chat-distribuido y ejecutar:

docker compose -f docker-compose.lab.yml up -d --build

Eso levanta 3 cajas:

Opción B — El día de la sesión con el servidor del profesor

  1. Copiar .env.example como .env y llenar 3 datos:
    • GROUP_NAME: el nombre de nuestro servidor en el chat.
    • PUBLIC_URL: la dirección de nuestro portátil en la red del salón, ej. http://192.168.1.23:8000 (se ve con el comando ipconfig).
    • CENTRAL_URL: la dirección que dé el profesor.
  2. Ejecutar docker compose up -d --build y abrir http://localhost:8000.
  3. Si Windows pregunta por el firewall, permitir (el central debe poder entrar al puerto 8000).

3El viaje de un mensaje

1ana escribe "hola" en la página de ga
→
2ga le pone id único y número de Lamport, y lo guarda en disco (historial + outbox)
→
3Una tarea de fondo lo envía al central: POST /messages
→
4El central lo guarda y se lo reenvía a los demás: POST /fed/messages
→
5gb revisa el id: si es nuevo lo guarda y lo muestra; si ya lo tenía, lo ignora

Si en el paso 3 el central no responde, el mensaje se queda en el outbox y se reintenta: después de 1 s, 2 s, 4 s, 8 s… hasta 30 s entre intentos.

4Las 6 ideas clave

① Persistencia

Todo se guarda en un archivo de base de datos (SQLite) dentro de un volumen de Docker: una carpeta que sobrevive aunque se apague o reinicie la caja. Así no se pierden usuarios ni mensajes.

Requisito 2

② Outbox (buzón de salida)

Cuando alguien escribe, el mensaje se guarda primero en disco en una "bandeja de salida". Después se intenta enviar. Si el servidor se muere justo en ese momento, al volver el mensaje sigue ahí.

Requisito 6

③ Reintentos con espera creciente (backoff)

Si el central no contesta o contesta con error 5xx, se reintenta esperando cada vez el doble (1, 2, 4, 8… s). Si contesta 4xx ("tu mensaje está mal"), no se reintenta: sería inútil.

Requisitos 5 y 6

④ Id único y deduplicación

Cada mensaje nace con un UUID (un código larguísimo que nunca se repite). Si nos llega un id que ya tenemos, respondemos "OK" pero no hacemos nada. Por eso reintentar nunca muestra mensajes repetidos.

Requisito 6

⑤ Reloj de Lamport

Un contador que reemplaza a la hora. Al enviar: contador + 1. Al recibir un mensaje con número N: contador = el mayor entre (mi contador, N) + 1. Los mensajes se muestran ordenados por ese número (y si empatan, por el nombre del servidor). Así todos ven el mismo orden.

Requisito 7 · libro cap. 8

⑥ Heartbeat y recuperación

Cada 3 s le preguntamos al central "¿estás vivo?" (GET /health). Si falla 3 veces seguidas, lo damos por caído y dejamos de enviar. Cuando vuelve: nos registramos de nuevo, pedimos lo que nos perdimos (GET /history) y enviamos lo pendiente.

Requisitos 8 y 9 · libro cap. 7

La frase para recordar: "al menos una vez" (reintento hasta que llegue) + "idempotencia" (lo repetido no tiene efecto) = el usuario ve cada mensaje exactamente una vez.

6El código importante, línea por línea

a) Guardar un mensaje nuevo — db.py → create_local_message

lamport = _get_clock() + 1          # regla de Lamport al ENVIAR: sumar 1
_set_clock(lamport)                 # guardar el nuevo valor del reloj
msg = {"id": str(uuid.uuid4()),      # id único que nunca cambia
       "from": f"{user}@{GROUP_NAME}",
       "origin": GROUP_NAME,
       "lamport": lamport, ...}
_insert_message(msg, via="local")   # 1) al historial (para mostrarlo)
INSERT INTO outbox ...              # 2) a la bandeja de salida (para enviarlo)
COMMIT                              # todo junto o nada: no queda a medias

En simple: sube el contador, arma el mensaje con su id, lo guarda para mostrar y lo deja en la bandeja de salida. Las 3 cosas pasan "de un solo golpe" (transacción).

b) Recibir un mensaje de otro grupo — db.py → store_remote_message

exists = SELECT 1 FROM messages WHERE id = ?
if exists:
    return False                    # ya lo tenía: no hago nada (deduplicación)
local = max(_get_clock(), msg["lamport"]) + 1   # regla de Lamport al RECIBIR
_set_clock(local)
_insert_message(msg, via="push")

Y en main.py la puerta POST /fed/messages responde 200 tanto si era nuevo como si era repetido: eso es la idempotencia.

c) Enviar con reintentos — federation.py → deliver

r = POST {CENTRAL_URL}/messages con el mensaje
si responde 2xx  → borrar del outbox, log "SENT"
si responde 4xx  → borrar del outbox, log "REJECTED"   # está mal: no insistir
si 5xx o no hay respuesta →
    espera = min(30, 1 × 2^intentos)  ± 20 %            # 1, 2, 4, 8, 16, 30 s
    reprogramar, log "RETRY"

El "± 20 %" (jitter) evita que todos los grupos reintenten exactamente al mismo tiempo y saturen al central.

d) ¿Está vivo el central? — federation.py → heartbeat_loop

cada 3 segundos:
    pregunto GET /health
    si responde: fallos = 0
        si estaba "caído" → "CENTRAL_UP": me registro, pido /history, libero el outbox
    si no responde: fallos += 1
        si fallos ≥ 3 → "CENTRAL_DOWN": dejo de enviar (lo pendiente queda en disco)

e) Recuperar lo perdido — federation.py → recover_history

since = (mayor lamport que recibí de otros) − 100     # pedimos "de más" a propósito
GET {CENTRAL_URL}/history?since=since
por cada mensaje: guardarlo si es nuevo (los repetidos se ignoran solos)

¿Por qué "− 100"? Un grupo con el contador atrasado pudo mandar mensajes con números menores que el nuestro. Si pidiéramos exactamente desde nuestro número, nos los saltaríamos. Pedir de más no hace daño porque los repetidos se botan.

7El experimento y la interoperabilidad

Experimento: "¿se pierden mensajes si se cae nuestro servidor?"

  • gb manda 5 mensajes por segundo. A los 4 s "matamos" a ga durante 2, 5 o 10 s y lo prendemos de nuevo.
  • Al central le pusimos fallos a propósito: 10 % de respuestas perdidas y 10 % de mensajes reenviados dos veces.
  • Lo hicimos con recuperación de historial y sin ella (control), 3 veces cada caso: 18 corridas.
CaídaPerdidos CON recuperaciónPerdidos SIN recuperaciónRepetidos en pantalla
2 s0 · 0 · 00 · 1 · 2 (1,6 %)0
5 s0 · 0 · 04 · 1 · 5 (4,4 %)0
10 s0 · 0 · 025 · 63 · 24 (37 %)0

Conclusión: con nuestro diseño no se pierde ni se repite nada. Llegaron 425 duplicados reales y todos se botaron por id. Sin pedir el historial, mientras más dura la caída, más se pierde.

Ensayo de interoperabilidad

Como la sesión de clase todavía no ha sido, la ensayamos con 4 "grupos": dos copias del nuestro y dos programas escritos aparte (uno bien hecho y otro con errores típicos). Resultado: todos vieron todos los mensajes; en las caídas por turnos nadie perdió nada. Pero el grupo con errores ordena por orden de llegada (ve un orden distinto) y pierde todo su historial al reiniciar porque lo guarda en memoria y no en disco.

9Glosario

Servidor / endpointPrograma que espera peticiones. Un endpoint es una "puerta" (ej. POST /fed/messages).
HTTP 2xx / 4xx / 5xxRespuestas: 2xx = bien; 4xx = la petición está mal (culpa de quien envía); 5xx = el servidor falló (culpa de quien recibe).
JSONFormato de texto para mandar datos: {"from": "ana@ga", "body": "hola"}.
Docker / contenedorCaja que trae el programa con todo lo que necesita. Volumen: carpeta de la caja que no se borra.
FastAPILibrería de Python para hacer servidores web (la vimos en el taller del curso).
SQLiteBase de datos que vive en un solo archivo.
UUIDIdentificador aleatorio tan largo que nunca se repite.
IdempotenteHacerlo una vez o diez veces da el mismo resultado.
Backoff exponencialReintentar esperando el doble cada vez. Jitter: un poquito de azar en la espera.
Reloj de LamportContador lógico que ordena eventos sin usar la hora real (libro, cap. 8).
Heartbeat / pingPreguntar periódicamente "¿estás vivo?" para detectar caídas (libro, cap. 7).
OutboxBandeja de salida en disco con lo que falta por enviar.
